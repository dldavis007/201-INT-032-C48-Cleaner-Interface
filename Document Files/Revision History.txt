Rev 3.07 8/25/2021	    DLD
		Fixed a problem with the program slowing down and not sending Speed control commands fast enough.
		This problem happens when the Linear Actuator is not fully retracted.
		The problem was thought to be the following:
		
			The Stop_LA function had a 50ms delay, this delay makes sure the PWM outputs are low when
			the function is exited (not sure why this is required).  The PWM period appears to be 6.41ms,
			so I changed the 50ms delay to 10ms.
			
			Once the Actuator had made a movement, the Stop_LA function was always being called. I changed 
			this to only call the function if "done" was "0" (no longer constantly called).  
			
			The problem was that constantly calling the Stop_LA function, introduced a 50ms delay everytime
			the program went through the main loop.  
			
			This means that the MCO_ProcessStack function was only getting called about 20 times a second.  
			The MCO_ProcessStack function cycles through the TPDOs that need to be sent 1 at a time each 
			time it is called.  If there are 8 TPDOs (typical for most of the latest programs), then it 
			takes 8 calls to the MCO_ProcessStack function to get all 8 TPDOs sent out.  So, a 50ms delay 
			between each call will result in any one particular TPDO from being transmitted any faster 
			than 400ms (8 calls times 50ms between calls equals 400ms).
			
			As a general rule, any delays in the "Main Loop" need to be a maximum of 1/8 the fastest
			re-occuring TPDO time.  We have typically had our fastest TPDO times down around 100ms, so
			delays in the main loop should be no greater than 12ms (10ms would probably be a better value).
			A one time delay (not re-occuring in each loop) of longer than 12ms may be acceptable if you 
			are not concerned with an occasional extended time on one of the re-occuring TPDOs.

3.25	07-29-25		DLD
	Corrected critical flaws in the state machine logic for all timed movements to resolve a system hang.

	- **Problem 1: Indefinite Hang.** The safety timer (`SequenceTimer`) was only initialized if it was already zero. 
		This created a condition where a stale value from a prior operation or a calculated value of zero would prevent the timer from starting. 
		If the hardware stalled, the system would hang indefinitely instead of timing out.
	- **Problem 2: Missed Timeouts.** A race condition existed where a successful movement would clear the timer before a pending timeout was processed, 
		causing the error state to be missed.
	- **Fix:** The logic was refactored to unconditionally set the timer at the start of every timed operation and to guarantee it holds a positive value. 
		The timer is now only cleared after a successful sequence is fully complete.
